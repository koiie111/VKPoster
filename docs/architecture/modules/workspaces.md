# Workspace, команда, роли, аудит (этап 04)

Все данные принадлежат workspace (пространству). Доступ определяет роль участника.

## Модель
- `workspaces`: `public_id` (ULID, единственный id в URL), `owner_id`, название, часовой пояс, язык, `is_personal`.
- `workspace_members`: PK `(workspace_id, user_id)`, `public_id` (ULID участника для URL), роль, `channels_restricted`.
- `invitations`: адрес, роль, `token_hash` (SHA-256), срок 7 дней, `accepted_at`, `revoked_at`.
- `member_channel_access`: каналы, доступные ограниченному участнику (FK на `channels` добавит этап 06).
- Личное пространство создаётся при регистрации (почта и соцсеть); у остальных (админ-команда, сидеры) лениво при первом заходе в `/app` (`WorkspaceService::homeFor`). Лимит владения: 10 пространств (`OWNED_LIMIT`, тарифные лимиты придут с биллингом).
- Удаление аккаунта владельца каскадно удаляет его пространства (решение этапа 04; сценарий удаления аккаунта с передачей владения — задача будущих этапов).

## Роли и права
Матрица в `config/permissions.php` (читается `Permissions`; неизвестное право бросает исключение). Роли: owner, admin, editor, author, viewer, client. Иерархия «кто кем управляет» — `MemberPolicy`: управлять можно только теми, кто ниже по рангу, и выдавать роли ниже своей. Владельца нельзя понизить, исключить или пригласить: владение передаётся только `transferOwnership` (старый владелец становится admin). Так в пространстве всегда ровно один owner. Клиент всегда ограничен назначенными каналами; у остальных ограничение включается явно (`ChannelAccessRepository::set`). Интерфейс назначения каналов появится с каналами (этап 06).

## Запрос
`/w/{workspaceId}/…` → `Authenticate` → `RequireVerifiedEmail` → `ResolveWorkspace` (чужое или несуществующее пространство → 404) → `Authorize` (`[Authorize::class, ['permission' => '…']]`, нет права → 403) → контроллер. В Twig: `can('право')`, `current_workspace()`, `my_workspaces()`, `workspace_nav()`.

## Изоляция данных
- `WorkspaceContext` создаётся только из пары `Workspace` + `Membership`.
- Репозитории данных пространства наследуют `WorkspaceScopedRepository`; правило PHPStan `WorkspaceScopedRepositoryRule` требует `WorkspaceContext` первым параметром каждого публичного метода. `scoped()` сразу добавляет `workspace_id`.
- Поиск без контекста (по публичному id, по токену приглашения) вынесен в `WorkspaceRepository` и `InvitationLookup`.
- Обходной тест `WorkspaceAccessTest` проходит по всем маршрутам `/w/…`: чужое пространство → 404, гость → `/login`, каждая роль получает ровно положенное. Новый маршрут попадает под него автоматически.

## Приглашения
Админ вводит почту и роль → письмо со ссылкой `/invitations/{token}` (43 символа, в БД только хэш). Новое приглашение на тот же адрес отзывает старое. Страница публична; гостю предлагает войти или зарегистрироваться и возвращает обратно (`auth.intended`). Принять можно только вошедшим пользователем с подтверждённой почтой; если у аккаунта другая почта, отказ. Ссылка одноразовая (атомарный `UPDATE`). Не больше 20 приглашений в час на пространство. Просроченные чистит `auth:prune`.

## Журнал
`AuditLog::record(action, actorId, subjectType, subjectId, meta, workspaceId)`. Страница «Журнал действий» (`audit.view`: owner и admin) показывает записи с `workspace_id` пространства: фильтры по группе событий, участнику, датам; 50 записей на страницу. События входа остаются в личном журнале на странице «Безопасность». Новые события добавлять в `AuditActions` (название и описание); в `meta` только скаляры, без секретов. События: `workspace.{created,updated,deleted,ownership_transferred}`, `member.{invited,invitation_revoked,joined,role_changed,removed,left}`.

## Настройки
Название, часовой пояс, язык (`workspace.settings`); удаление (`workspace.delete`) и передача владения требуют ввести название пространства.
