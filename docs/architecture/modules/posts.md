# Посты, календарь и публикация (этап 07)

Ядро продукта: пост → варианты под каналы → план → надёжная публикация. Код: `src/Domain/Post`, `src/Domain/Notification`, `src/Http/Controllers/Posts`, шаблоны `templates/workspace/posts/`, компоненты `templates/components/composer.twig`, `calendar.twig`, скрипты `public/assets/js/editor.js`, `calendar.js`.

## Таблицы
- `posts`: пост пространства. `status` (`draft | scheduled | publishing | published | partially_failed | failed | cancelled`) **не ставится вручную**: его считает `PostStatusAggregator` по публикациям. `base_text` (разметка редактора), `media_ids_json` (публичные id файлов медиатеки по порядку), `options_json` (кнопки, тихая отправка, превью, закрепление, удаление через N минут, первый комментарий), `per_network`, `scheduled_at` (UTC), `timezone` (пояс пространства в момент планирования).
- `post_variants`: по одному на канал. `text`, `media_ids_json`, `options_json` равны NULL, пока вариант следует общему посту (`PostVariant::resolve()`). `platform` и `channel_name` — снимок: после отключения канала `channel_id` становится NULL, история читается.
- `publications`: один вариант, одна отправка. `status` `queued | sending | sent | failed | unknown | cancelled`, `attempt`, `due_at` (когда должна была выйти: от него считается задержка), `run_at` (когда можно начинать следующую попытку), `enqueued_at` (есть задание в очереди), `idempotency_key` (UNIQUE), `external_post_id`, `external_ids_json` (все сообщения, у альбома их несколько), `external_url`, ошибка для человека (`error_message`) и техническая (`error_detail`, только владельцу и администратору), `delete_at`/`deleted_at`/`delete_error`, `pinned`.
- `publication_attempts`: журнал попыток (исход, класс ошибки, сообщение, детали).
- `post_templates`: шаблон = `PostDraft` в JSON. `notifications`, `notification_settings`, `telegram_links`, `telegram_link_tokens`: уведомления.

## Конвейер (мастер-план §4.4)
1. Планирование (`PostService::schedule`): проверка каждого канала (`PostValidator`: адаптер, файлы, опции, статус канала), создание `queued`-публикаций. «Сейчас» сразу кладёт `PublishJob` (очередь `publish`).
2. Планировщик раз в минуту (`PublicationScheduler::tick`): для публикаций, которые наступят в ближайшие 90 секунд, создаёт `PublishJob` с задержкой до нужного момента (поэтому пост выходит вовремя, а не на следующем тике); потерявшиеся задания создаёт заново; зависшие в `sending` 15 минут переводит в `unknown`; ставит удаления по таймеру.
3. `Publisher::run`: замок Redis на публикацию → **claim** в БД (`queued → sending`, ровно один победитель, только если `run_at` наступил) → канал на паузе/сломан = отказ без вызова сети; проверка канала перед публикацией, если последняя старше `CHANNEL_PREFLIGHT_MINUTES` → валидация → сборка `PublishRequest` (текст в формате платформы, файлы во временные пути, тяжёлое фото заменяется уменьшенным) → `adapter->publish`.
4. Исходы по `ErrorKind`: temporary/rate_limited → `queued` с задержкой 1/5/15/60 мин (или `Retry-After`), до 5 попыток; auth → `failed` + канал `error`; permanent → `failed` + внеочередная проверка канала; unknown_outcome и любое неожиданное исключение во время вызова → `unknown`, **без автоповтора** (дубль хуже пропуска). Успех: `sent`, все id, ссылка, таймер удаления; закрепление и первый комментарий выполняются «по возможности» и не делают пост неудачным.
5. Статус поста пересчитывается под блокировкой строки поста; журнал аудита `post.published`, уведомления, метрика `publish.latency` в логе (секунды от `due_at` до отправки).

Состояния публикации и разрешённые переходы заданы в `PublicationStatus` (тест перебирает все пары). `PublicationSystem::move()` меняет статус только если строка ещё в ожидаемом состоянии. `unknown` продолжают только люди: «пост вышел», «поста нет» или «опубликовать ещё раз» (страница поста).

## Разметка текста
`**жирный**`, `*курсив*` или `_курсив_`, `~~зачёркнутый~~`, `[текст](https://…)`, `\*` — экранирование. `TextFormatter` превращает её в HTML Telegram (всё остальное экранируется, ссылки только http/https), в простой текст (ссылка как `текст (адрес)`) и «видимый» текст для счётчиков. Грамматика продублирована в `editor.js` для превью; тест `PostValueObjectsTest::formats` перечисляет случаи. `Capabilities::$textFormat` говорит, какой формат нужен платформе.

## Права
`calendar.view` — календарь и страница поста; `posts.draft` (автор и выше) — редактор, черновики, дубли, шаблоны; `posts.publish` (редактор и выше) — планирование, перенос, отмена, повтор. Автор правит только свои черновики. Участник с ограничением (и клиент) видит и использует только назначенные каналы. Всё, что принимает объект поста, проверяет его пространство ещё раз (`PostService::canSee`).

## Время
Дата и время вводятся в поясе пространства с явной подписью. `ScheduleTime::parse` отклоняет прошлое, несуществующие даты и время, пропущенное переводом часов (весной); осенью двойной час берётся первым вхождением. В БД всё в UTC.

## Редактор (`editor.js`)
Один компонент Alpine `composer`: чипы каналов; переключатель «отдельно для каждой соцсети» с вкладками на канал (вариант наследует общий текст, файлы и опции, пока их не изменили: скрытые поля `*_custom`); панель форматирования и горячие клавиши; счётчики лимитов; медиа (выбор из медиатеки через `/media-picker`, загрузка на лету, порядок перетаскиванием и стрелками); кнопки-ссылки; живое превью по каналам; проверка на сервере (`/posts/validate`, 700 мс после правки); автосохранение черновика (`/posts/autosave`, 4 с, без записи в журнал аудита). Опции показываются по `Capabilities` выбранных платформ.

## Календарь
`CalendarController` рендерит месяц, неделю и список на сервере в поясе пространства; фильтры по каналу, статусу, автору; перенос перетаскиванием вызывает `POST /posts/{id}/move` (время суток сохраняется, пост проверяется заново). Дублирование, отмена, возврат в черновики, удаление (опубликованное удалить нельзя, его удаляют из соцсети).

## Уведомления
`Notifier`: ошибка публикации (автору, владельцу и администраторам), проблема с каналом (владельцу и администраторам, письмо из этапа 06), успех (только автору, по умолчанию выключено). По почте и в Telegram; настройки: «Уведомления» в аккаунте. Привязка Telegram: страница выдаёт одноразовый токен (в БД только SHA-256, 15 минут), человек открывает `t.me/<бот>?start=<токен>`, бот в `TelegramUpdateHandler` связывает чат с аккаунтом. Отправка идёт через очередь.

## Команды и проверка
`bench:publish --fake [--count=200] [--spread=30]`: планирует N постов в тестовую сеть в одноразовом пространстве, гоняет планировщик и воркер в реальном времени, печатает p50/p95/max задержки (DoD: p95 < 60 с; на локальном прогоне 200 постов p95 меньше секунды). Останавливайте `worker` и `scheduler` на время замера.

## Отличия от плана
- Повтор после временной ошибки — это `sending → queued` со сдвинутым `run_at`, а не отдельный статус `failed-retryable`.
- Постоянная ошибка отмечает канал сломанным только если это ошибка доступа; при отказе по содержимому канал перепроверяется (`ChannelHealthService::check`) и помечается, если он действительно сломан.
- Редактирование опубликованного: `EditableAdapter` (сейчас Telegram и тестовая сеть), только текст или подпись.
