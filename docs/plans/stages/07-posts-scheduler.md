# Этап 07 — Редактор, календарь, планировщик, публикация

**Зависимости:** 05, 06 · **Ветка:** `stage-07-posts-scheduler`

## Цель
Ядро продукта: создать пост → выбрать каналы → настроить вариант под каждую сеть → запланировать → надёжно опубликовать (мастер-план §4.4).

## БД
`posts`, `post_variants`, `publications`, `post_templates`, `notifications`, `notification_settings`.

## Задачи
- [ ] Редактор:
  - общий текст + переключатель «настроить отдельно для каждой сети» (варианты наследуют общий текст, пока его не изменили);
  - выбор каналов (с группировкой по платформам);
  - медиа из медиатеки или загрузка на лету, порядок перетаскиванием;
  - опции по `capabilities` платформы: кнопки-ссылки, тихая отправка, отключение превью ссылок, закрепить, удалить через N часов, первый комментарий (там, где есть);
  - живое превью «как будет выглядеть» для каждой сети; счётчики символов с лимитами; валидация `adapter->validate()` до сохранения;
  - Markdown-подобная разметка (жирный, курсив, ссылка) → конвертация в формат каждой платформы (TG HTML, MAX markdown/html, VK plain);
  - автосохранение черновика.
- [ ] Планирование: «сейчас», «на дату/время» (в часовом поясе workspace, с явной подписью пояса), «в черновики»; дата в прошлом запрещена.
- [ ] Календарь: месяц, неделя, список; фильтры по каналу, статусу, автору; перенос перетаскиванием (с повторной валидацией); дублирование поста.
- [ ] Конвейер публикации ровно по мастер-плану §4.4: `schedule:run` → `PublishJob` → блокировка → адаптер → классификация ошибок → backoff → статус поста агрегируется из публикаций (`published`, `partially_failed`, `failed`).
- [ ] Идемпотентность: `publications.idempotency_key`; переход статусов только допустимый (state machine с тестами); исход `unknown_outcome` → без автоповтора.
- [ ] Редактирование и отмена запланированного поста до начала отправки; редактирование опубликованного (если платформа умеет — TG `editMessage*`).
- [ ] Удаление по таймеру (`delete_after`) — отложенная задача.
- [ ] Журнал публикаций: попытки, ошибки человеческим языком + технические детали для admin.
- [ ] Уведомления: email и Telegram (тот же бот, привязка аккаунта через `/start <token>`) при ошибке публикации, проблеме с каналом, (опционально) успешной публикации; настройки по типам.
- [ ] Шаблоны постов (сохранить как шаблон / создать из шаблона).
- [ ] Метрика задержки публикации (scheduled → sent) в логах.

## Тесты
State machine публикации (все переходы); воркер падает после отправки → `unknown`, без дубля; 429 → повтор через `retry_after`; permanent → без повтора + уведомление; два воркера одновременно → один вызов адаптера; часовые пояса и переход на летнее время (тест с поясом, где он есть, например Europe/Berlin); перенос в календаре с невалидным для платформы содержимым → отказ; автор без права публикации не может запланировать.

## Проверка владельцем
1. Запланировать в подключённый TG-канал: текст с форматированием, альбом из 3 фото, пост с кнопкой, пост с «удалить через 1 час» (временно можно поставить 5 минут). Всё вышло вовремя и выглядит как в превью?
2. Удобен ли редактор? Чего не хватает?

## DoD
Реальные публикации в TG проходят у владельца; задержка p95 < 60 с в локальном прогоне на 200 постов (скрипт `bin/console bench:publish --fake`).
