# Этап 20 — Полная админ-панель владельца, бизнес-дашборд и статистика

**Зависимости:** 10, 11 · **Ветка:** `stage-20-owner-admin`
**Место в очереди:** сразу после этапа 11 (см. таблицу в PROGRESS.md). Этапы 12–19 после него обязаны добавлять в админку свои разделы и метрики (ENGINEERING_RULES §7).

## Цель
Владелец видит и контролирует весь бизнес из одной панели `/admin`: деньги, пользователей, платформы, нагрузку, контент сайта и поддержку. Этап 11 даёт базовую админку, этот этап делает её полной.

## БД
`staff_roles`, `staff_members` (пользователь + роль персонала), `analytics_events`, `metrics_daily`, `admin_notes`, `announcements`, `support_tickets`, `support_messages`, `email_campaigns`, `email_campaign_recipients`, `cms_pages`, `cms_blocks`, `app_settings`, `data_requests` (запросы по 152-ФЗ).

## Задачи

### 1. Доступ и безопасность админки
- [ ] Роли персонала (RBAC): `superadmin`, `finance` (платежи и возвраты), `support` (пользователи, тикеты, без денег), `content` (CMS, рассылки), `analyst` (только чтение дашбордов). Права — в `config/admin_permissions.php`, проверка в каждом контроллере админки.
- [ ] Обязательная 2FA, повторный ввод пароля или кода для опасных действий (возврат, блокировка, начисление, impersonation, смена цен), опциональный allowlist IP (`ADMIN_IP_ALLOWLIST`), отдельный короткий idle-таймаут сессии (30 мин).
- [ ] **Каждое** действие в админке пишется в аудит (кто, что, до/после, IP); журнал аудита админки с фильтрами и экспортом.

### 2. Главный дашборд (бизнес)
- [ ] Сбор событий: серверная таблица `analytics_events` (`user_registered`, `email_verified`, `channel_connected`, `first_post_scheduled`, `first_post_published`, `trial_started`, `subscription_started/renewed/upgraded/downgraded/cancelled/expired`, `payment_succeeded/failed/refunded`, `ai_used`, `referral_signup` …) + UTM и referrer первого визита (cookie first-touch, сохраняется при регистрации). Без сторонних трекеров в приложении (152-ФЗ); на лендинге — Яндекс Метрика только после согласия на cookies (опция).
- [ ] Ежедневная агрегация в `metrics_daily` (задача планировщика, пересчёт за последние 3 дня, идемпотентна); дашборд читает агрегаты, а не сырые таблицы.
- [ ] KPI-карточки с сравнением с прошлым периодом: **MRR, ARR, выручка** (по дням и провайдерам, в рублях, валюты отдельно), **новые регистрации, активированные пользователи** (подключил канал и опубликовал), **DAU/WAU/MAU**, **платящие**, **конверсия trial → paid**, **churn** (логовый и выручки), **ARPU / ARPPU, LTV**, **возвраты**.
- [ ] Графики: выручка и MRR во времени (новый, расширение, сокращение, отток), регистрации по источникам (UTM), распределение по тарифам, **воронка** (визит → регистрация → подтверждение email → канал → первый пост → оплата), **когорты удержания** по неделям или месяцам.
- [ ] Фильтры: период (сегодня / 7 / 30 / 90 дней / год / произвольный), тариф, платформа, источник.
- [ ] Ежедневный отчёт владельцу в Telegram и на email (выручка, регистрации, оплаты, ошибки публикаций, длина очереди), время отправки — в настройках.

### 3. Операционная статистика
- [ ] Публикации: всего, по платформам, успешность (%), ошибки по типам и платформам, задержка публикации p50/p95, топ проблемных каналов и workspace.
- [ ] Платформы: доля ошибок API по часам (раннее обнаружение падения VK/TG/MAX/IG), rate limit, состояние подключений (сколько каналов в `error`/`revoked`), feature-флаги.
- [ ] Система: очередь (длина, возраст старейшей задачи, throughput), failed jobs (просмотр, повтор, удаление), scheduler heartbeat, MySQL/Redis/диск/хранилище, версия и время деплоя, последние ошибки из лога (без секретов).
- [ ] AI: запросы, расход кредитов, **себестоимость у LLM-провайдера и маржа**.
- [ ] Хранилище: объём по workspace, топ-потребители.

### 4. Пользователи и workspace
- [ ] Поиск (email, имя, id, VK/TG id, домен почты), фильтры (тариф, статус, дата регистрации, источник, активность), сортировки, экспорт CSV.
- [ ] Карточка пользователя: профиль, способы входа, сессии, workspace и роли, подписка и история платежей, каналы, последние публикации и ошибки, AI-кредиты, баланс ledger, рефералы, тикеты, заметки персонала, журнал аудита.
- [ ] Действия: заблокировать или разблокировать (с причиной, пользователь видит сообщение), разлогинить везде, сбросить 2FA (только superadmin, с повторным подтверждением), подтвердить email, сменить тариф или продлить вручную, начислить дни, кредиты или баланс (только через ledger с обязательной причиной), impersonation (с баннером, без доступа к смене пароля и платёжным данным, ограничен по времени).
- [ ] Запросы по 152-ФЗ: выгрузка данных пользователя (JSON/ZIP), удаление или анонимизация аккаунта с сохранением финансовых записей, которые требует закон.

### 5. Финансы
- [ ] Платежи (все провайдеры): фильтры, статусы, детали, сырой вебхук (с маскированием), сверка с провайдером (`fetchStatus`), возврат полный или частичный.
- [ ] Подписки: активные, trial, в grace, отменённые; ручные операции.
- [ ] Счета и чеки, выгрузка для бухгалтерии (CSV/XLSX за период: дата, сумма, провайдер, комиссия, чек).
- [ ] Журнал вебхуков: просмотр, повторная обработка.
- [ ] Редактор тарифов, цен (по валютам и периодам), лимитов и пакетов; изменения цены не затрагивают действующие подписки до продления; история изменений.
- [ ] Промокоды (создание, статистика использования и выручки), реферальная программа (начисления, заявки на вывод → одобрить или отклонить, антифрод-флаги).

### 6. Контент сайта и коммуникации
- [ ] CMS: тексты лендинга, FAQ, статьи базы знаний (markdown → санитизированный HTML), юридические документы с версиями (новая версия → запрос повторного согласия).
- [ ] Объявления в приложении (баннер: всем, по тарифу, по платформе; период показа).
- [ ] Email-рассылки: сегмент (тариф, активность, платформа), шаблон, тестовая отправка, отправка через очередь с лимитом скорости, отписка в один клик (`List-Unsubscribe`), статистика (отправлено, ошибки, отписки). Только пользователям с маркетинговым согласием.
- [ ] Шаблоны системных писем (редактирование текста с превью).

### 7. Поддержка
- [ ] Тикеты из формы «Сообщить о проблеме» и из Telegram-бота: статусы, назначение, ответы (письмом или в TG), внутренние заметки, авто-контекст (тариф, последние ошибки публикаций).

### 8. Настройки сайта
- [ ] Режим обслуживания (с разрешённым доступом персонала), включение и выключение регистрации и инвайт-режима, глобальные лимиты, контакты поддержки, реквизиты. Хранятся в `app_settings` с кэшем в Redis; секреты здесь **не** хранятся (только env).

### 9. Демо-данные
- [ ] `make seed-demo` (только `APP_ENV=local`): 500 пользователей, workspace, каналы, публикации и платежи за 6 месяцев с реалистичным распределением, для проверки дашборда и нагрузки на агрегацию.

### 10. UI админки
- [ ] Отдельный layout, боковое меню по разделам с учётом прав роли, глобальный поиск (пользователь, платёж, workspace по id или email), таблицы с серверной пагинацией, сортировкой и фильтрами, графики Chart.js (из vendor), тёмная тема.

## Тесты
- Матрица доступа: каждая роль персонала × каждый раздел (обходной тест всех маршрутов `/admin/*`, как IDOR-тест этапа 04); обычный пользователь → 404 на всех.
- Опасные действия без повторного подтверждения → отказ; все действия попадают в аудит.
- Метрики: MRR, churn, конверсия, когорты считаются верно на синтетическом наборе данных с известным ответом (фикстура «эталонный месяц»).
- Агрегация идемпотентна (двойной запуск не меняет результат).
- Начисления только через ledger, сумма проводок по счёту = баланс.
- Рассылка не уходит пользователям без согласия; отписка работает без входа.
- Выгрузка по 152-ФЗ содержит данные только этого пользователя.

## Проверка владельцем
1. Войти в `/admin` (создать суперадмина: `make console CMD="user:create-admin you@example.com"`), пройтись по разделам на сидовых данных (`make seed-demo` создаёт 500 пользователей, платежи и публикации за 6 месяцев).
2. Каких метрик или разделов не хватает? Что лишнее?
3. В какое время и куда присылать ежедневный отчёт?
4. Нужны ли роли персонала сейчас или пока только вы (superadmin)?

## DoD
Все разделы работают на демо-данных, метрики сходятся с эталонной фикстурой, владелец подтвердил состав дашборда.
