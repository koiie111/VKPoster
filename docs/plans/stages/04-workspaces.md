# Этап 04 — Workspace, команда, роли, аудит

**Зависимости:** 02 · **Ветка:** `stage-04-workspaces`

## Цель
Мультиарендность: все данные принадлежат workspace; доступ определяется ролью участника.

## БД
`workspaces`, `workspace_members`, `invitations`, `audit_log`.

## Задачи
- [ ] При регистрации создаётся личный workspace (owner).
- [ ] Переключатель workspace в шапке; текущий workspace в URL (`/w/{workspaceId}/...`) — middleware `ResolveWorkspace` проверяет членство (не член → 404).
- [ ] Роли и права (матрица в `config/permissions.php`):
  | Право | owner | admin | editor | author | viewer | client |
  |---|---|---|---|---|---|---|
  | биллинг, удаление workspace | ✓ | | | | | |
  | участники, каналы | ✓ | ✓ | | | | |
  | публиковать и планировать | ✓ | ✓ | ✓ | | | |
  | создавать черновики, отправлять на согласование | ✓ | ✓ | ✓ | ✓ | | |
  | смотреть календарь и аналитику | ✓ | ✓ | ✓ | ✓ | ✓ | (только назначенное) |
- [ ] `Policy`-классы + `Authorize` middleware + хелпер `can()` в Twig.
- [ ] Базовый `WorkspaceScopedRepository`: метод без `WorkspaceContext` нельзя вызвать (проверка на уровне типа).
- [ ] Приглашения по email (токен-хэш, TTL 7 дней, принятие → вход/регистрация → членство), отзыв приглашения, смена роли, исключение участника, выход из workspace, передача владения.
- [ ] Ограничение доступа участника конкретными каналами (как в ecotime: «права на публикацию без админства в сообществе»): `member_channel_access`.
- [ ] `AuditLogger`: события входа, смены ролей, подключения каналов, публикаций, биллинга; страница журнала для owner/admin с фильтрами.
- [ ] Настройки workspace: название, часовой пояс, язык по умолчанию.

## Тесты
Матрица прав (data provider по всем ролям × действиям); IDOR: пользователь A не видит workspace B ни по одному маршруту (общий тест, который обходит все зарегистрированные маршруты `/w/{id}/…` с чужим id и ожидает 404); приглашение чужим токеном, истёкшее, повторное; нельзя понизить последнего owner.

## Проверка владельцем
Не требуется.
