# Правила разработки (обязательны для каждого агента и каждого этапа)

Нарушение любого пункта из §4 — повод **не мержить** этап.

## 1. Общие принципы
1. **Чистый PHP 8.3**, `declare(strict_types=1);` в каждом файле, PSR-4 (`App\` → `src/`), PSR-12 + php-cs-fixer.
2. Никаких фреймворков (Laravel, Symfony full-stack, Slim, Yii, CodeIgniter). Каркас наш, в `src/Kernel`.
3. Тонкие контроллеры: валидация входа → вызов сервиса из `Domain` → ответ. Бизнес-логика живёт в `Domain`, работа с внешними API — в `Integrations`.
4. Никаких глобальных переменных и `$_GET/$_POST/$_SESSION` вне `Kernel\Http\Request` и `Kernel\Session`. Зависимости передаются через конструктор (DI-контейнер).
5. Время — только через `Support\Clock` (в тестах `FakeClock`). В БД всё хранится в UTC (`DATETIME(6)`), в UI конвертируется в часовой пояс пользователя или workspace.
6. Деньги — целые копейки или центы (`BIGINT`) + код валюты; никаких float.
7. Идентификаторы во внешних URL — ULID/UUIDv7 (не автоинкремент), чтобы не перебирали.
8. Каждый внешний API — за интерфейсом, у которого есть **Fake-реализация** для тестов и dev.
9. Сообщения UI — на русском, через функцию перевода `t()` (на будущее под i18n); код, комментарии к коду и имена — на английском.
10. Архитектурные решения, которые отклоняются от плана, фиксируются в `docs/adr/NNNN-title.md`.

## 2. Белый список зависимостей Composer
Разрешено без согласования:
- prod: `twig/twig`, `guzzlehttp/guzzle`, `monolog/monolog`, `symfony/mailer`, `symfony/mime`, `phpoffice/phpspreadsheet` (импорт XLSX, этап 13), `league/flysystem` + `league/flysystem-aws-s3-v3`, `paragonie/constant_time_encoding`, `spomky-labs/otphp` (TOTP), `yoomoney/yookassa-sdk-php`, `stripe/stripe-php`, `ramsey/uuid` или `symfony/uid`, `vlucas/phpdotenv` (только dev), `ezyang/htmlpurifier` (если нужен HTML из rich-text).
- dev: `phpunit/phpunit`, `phpstan/phpstan` (+ `phpstan/phpstan-strict-rules`), `friendsofphp/php-cs-fixer`, `mockery/mockery`, `fakerphp/faker`.

- фронтенд (файлы в `public/assets/vendor` или бинарники в образе, фиксированные версии и SHA-256): Tailwind CSS standalone CLI, Alpine.js, htmx, Chart.js, Redoc, иконки Lucide, шрифт Inter (self-hosted). Никаких CDN и Google Fonts.
- инструменты (только в отдельном контейнере `tools/ui-snap`, не в приложении): Playwright, axe-core.

Любая другая библиотека — только с записью ADR (зачем нужна, почему не написать самим, проверка поддержки и CVE). `vendor/` **не коммитим** (меняется на этапе 00), `composer.lock` коммитим.

## 3. Тесты и качество
- `make check` = `cs` + `stan` (PHPStan level 8 + strict-rules) + `test` + `audit`. Всё запускается **в Docker**.
- Unit-тесты для доменной логики, Integration для репозиториев/миграций (настоящий MySQL `app_test`), Feature для HTTP через in-process `Application`.
- Каждая фича: happy path + ошибки валидации + **проверка авторизации** (гость → редирект/401, чужой workspace → 404, роль без прав → 403).
- Каждый адаптер внешнего API: тесты на записанных фикстурах (`tests/Fixtures/<platform>/*.json`) через мок HTTP-клиента; реальные вызовы только при ручной проверке.
- Покрытие новых классов в `Domain` и `Integrations` не ниже 80% (pcov).
- Миграции обратимы (`down`), тест: `migrate → rollback → migrate`.
- Ни один тест не ходит в интернет (HTTP-клиент в тестах падает при попытке реального запроса).

## 4. Чек-лист безопасности (self-review перед PR, копируется в описание PR)
- [ ] Все SQL — prepared statements; динамические имена колонок и сортировка — только из белого списка.
- [ ] Каждый запрос к данным workspace фильтрует по `workspace_id` текущего контекста; Policy проверена; есть тест на IDOR.
- [ ] Все state-changing маршруты — POST/PUT/PATCH/DELETE с CSRF (кроме вебхуков и API с токеном); GET ничего не меняет.
- [ ] Вывод только через Twig с автоэкранированием; нет `|raw` без санитайзера; нет inline `<script>`/`onclick` (CSP с nonce).
- [ ] Ввод валидируется по типу, длине, формату, перечислению; ошибки не раскрывают внутренности (нет stack trace, SQL, путей).
- [ ] Секреты (токены, ключи, пароли) не попадают в логи, ответы, исключения, git. Токены соцсетей и TOTP зашифрованы `Crypto`.
- [ ] Одноразовые токены (сброс, подтверждение, приглашение) хранятся как SHA-256 хэш, имеют TTL, одноразовые, сравниваются `hash_equals`.
- [ ] Rate limit на всё, что можно перебирать или что дорого.
- [ ] Редиректы только на относительные URL или URL из белого списка (нет open redirect).
- [ ] Загрузка файлов: размер, MIME по содержимому, пересжатие, хранение вне `public/`.
- [ ] Исходящие запросы по пользовательскому URL — через SSRF-guard.
- [ ] Вебхуки: проверка подписи до любой обработки, идемпотентность.
- [ ] Новые env-переменные добавлены в `.env.example` без реальных значений.
- [ ] `composer audit` чистый.

## 5. Git и процесс
1. Один этап = одна ветка `stage-NN-slug` = один PR. Мелкие осмысленные коммиты (Conventional Commits: `feat:`, `fix:`, `test:`, `chore:`, `docs:`, `refactor:`).
2. В конце каждого коммита: `Co-Authored-By: <агент> <noreply@...>` (как требует среда агента).
3. Никогда: `git push --force` в `main`, коммит в `main` напрямую, `--no-verify`, отключение или пропуск тестов ради зелёного CI, `git reset --hard` с потерей чужих (владельца) изменений.
4. PR: заголовок `Stage NN: <название>`, описание = что сделано + как проверить + чек-лист безопасности + что осталось или перенесено.
5. Merge: `gh pr merge --squash --delete-branch` **только** при зелёном CI и (если этап требует) после подтверждения владельца в PROGRESS.md.
6. Обновление `PROGRESS.md` делается **внутри ветки этапа** до merge (в `main` напрямую не коммитим).

## 6. Docker
- Всё (composer, php, тесты, миграции) — через `docker compose exec app …` или `make …`. На хосте PHP не нужен.
- Порты публикуются только на `127.0.0.1`.
- Dev-фичи (`DEV_LOGIN`, Fake-адаптеры, mailpit) включаются только при `APP_ENV=local` и невозможны при `APP_ENV=production` (проверка при старте приложения).

## 7. Документация и админка — часть каждой фичи
1. Документация обновляется в том же PR, что и код (мастер-план §7): модульный документ, схема БД, env-переменные, CHANGELOG, при необходимости статья в `docs/user/`.
2. У каждого класса в `src/` есть docblock с назначением класса; у публичных методов `Domain`, `Integrations`, `Kernel` — описание там, где сигнатуры недостаточно (`@throws`, побочные эффекты, единицы измерения, инварианты). Комментарии объясняют «почему», а не пересказывают код. Проверка: PHPStan-правило `RequireClassDocblockRule` (пишется на этапе 01).
3. `make docs` (phpDocumentor) должен собираться без ошибок; это часть `make check`.
4. Каждая новая пользовательская функция (начиная с этапа 20; до него — в базовую админку этапа 11) добавляет:
   - события в `analytics_events`, если она важна для воронки или выручки;
   - метрики в агрегацию `metrics_daily` и, при необходимости, виджет на дашборд;
   - раздел или колонки в админке для просмотра и ручного вмешательства (с проверкой прав персонала и аудитом).

## 8. UI/UX
1. Экраны собираются **только из компонентов дизайн-системы** (`templates/components/`). Нужного компонента нет — сначала добавить его в дизайн-систему и на витрину `/dev/ui`, потом использовать. Никаких разовых стилей в шаблонах страниц, кроме утилит Tailwind для раскладки.
2. Ключевые экраны повторяют утверждённые прототипы этапа 21. Отклонение — только с причиной в PR и вопросом владельцу.
3. Каждый экран и каждая асинхронная операция имеют 4 состояния: **загрузка** (skeleton или спиннер на кнопке, кнопка блокируется от двойного клика), **пусто** (empty-state с объяснением и действием), **ошибка** (что случилось и что сделать, введённые данные не теряются), **успех** (toast или явное изменение на экране).
4. Тексты — по `docs/design/ux-writing.md`: на «вы», дружелюбно, без канцелярита и технических терминов; кнопки «глагол + объект»; опасные действия — через confirm-dialog с названием объекта.
5. Формы: подписи у всех полей, подсказки к неочевидным, валидация на сервере (обязательно) и в браузере (для удобства), ошибка рядом с полем, фокус на первом ошибочном поле.
6. Адаптив от 360 px без горизонтального скролла; цели касания не меньше 44 px; всё доступно с клавиатуры, видимый фокус, `aria-*`; контраст WCAG AA в обеих темах.
7. Время всегда показывается с часовым поясом там, где это влияет на публикацию; даты — в формате пользователя (по умолчанию `ru-RU`).
8. **Визуальная проверка перед PR** для любого этапа с UI: `make ui-snap STAGE=NN` (скриншоты 375/768/1440 px × светлая/тёмная темы для URL этапа) и `make a11y` (0 нарушений serious/critical). Агент просматривает скриншоты сам и исправляет: обрезанный текст, наезды, пустые места, несогласованные отступы, нечитаемый контраст. В PR — список проверенных экранов; если этап ждёт владельца, путь к скриншотам указывается в вопросах.
9. UX-чек-лист в описании PR для этапов с UI:
   - [ ] только компоненты дизайн-системы, совпадает с прототипом;
   - [ ] 4 состояния у каждого экрана и действия;
   - [ ] тексты по ux-writing, нет технических ошибок в UI;
   - [ ] 360 px, клавиатура, тёмная тема, axe-core чистый;
   - [ ] скриншоты просмотрены, дефекты исправлены.
