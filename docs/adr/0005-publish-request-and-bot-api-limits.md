# 0005. `PublishRequest` вместо `PostVariant` и подключение Telegram без перечисления чатов

- Статус: принято
- Дата: 2026-10-04

## Контекст
Этап 06 задаёт контракты платформ раньше, чем появятся посты (этап 07). Мастер-план описывает `PlatformAdapter::publish(PostVariant, Channel, Credential, key)`, а режим «свой бот» — «выбор канала из тех, где бот админ». Но сущности `PostVariant` ещё нет, а Bot API не умеет перечислять чаты бота: есть только `getChat` по известному имени или номеру и поток апдейтов.

## Решение
1. Адаптеры принимают `PublishRequest` (текст, файлы как локальные пути, кнопки, опрос, тихая отправка, формат) и внешний id канала; этап 07 собирает запрос из варианта поста. Так адаптеры не зависят от схемы постов и тестируются без базы. `delete`/`pin` принимают `PublishResult`, потому что альбом Telegram состоит из нескольких сообщений и все их id нужны для удаления.
2. В режиме «свой бот» человек вводит токен и `@имя` (ссылку `t.me/…` или номер) канала, мы проверяем `getMe`, `getChat` и `getChatMember`. Выбор из списка потребовал бы вебхука на каждого бота клиента, а это сложнее и хрупче при почти том же удобстве.
3. Клиент Bot API свой, на `HttpClientInterface`: без новых зависимостей, ошибки классифицируются по правилам конвейера, токен не попадает в исключения.

## Последствия
- Этап 07 обязан сохранять `PublishResult::allIds` и передавать локальные файлы.
- Если позже понадобится список чатов бота клиента, добавим приём `my_chat_member` для свободных ботов отдельным ADR.
