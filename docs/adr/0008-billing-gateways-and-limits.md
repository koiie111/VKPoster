# 0008. Биллинг: свои клиенты платёжных систем, правила лимитов, проверка статуса вместо доверия вебхуку

- Статус: принято, требует живой проверки владельцем с тестовыми магазинами (см. «Что не проверено»)
- Дата: 2026-10-04

## Контекст
Этап 10 берёт деньги: тарифы с лимитами, пробный период, оплата и автопродление через ЮKassa и интернет-эквайринг Т-Банка, чеки 54-ФЗ. План этапа предлагал официальный SDK ЮKassa (он в белом списке зависимостей). Источник правды о подписке по мастер-плану §3.3 — наша БД, провайдеры только принимают деньги.

## Решение
1. **Свой тонкий клиент вместо SDK ЮKassa.** SDK ходит в сеть напрямую через cURL и не подменяется нашим `HttpClientInterface`; правило ENGINEERING_RULES §3 («ни один тест не ходит в интернет, адаптеры тестируются на записанных фикстурах») выполнить с ним нельзя без обходных путей. Нужны четыре вызова (`POST /payments`, `GET /payments/{id}`, `POST /refunds`, разбор уведомления), это ~150 строк, как и для VK и MAX. Т-Банк SDK не имеет вовсе. Зависимости не добавляются.
2. **Уведомление провайдера — только подсказка.** ЮKassa не подписывает уведомления, поэтому: проверка адреса отправителя по опубликованному списку (отключается только вне production флагом `YOOKASSA_VERIFY_IP=0`, например за туннелем) и обязательный повторный `GET /payments/{id}`. У Т-Банка уведомление подписано `Token`, но и в этом случае статус перепроверяется `GetState`. Сумма и валюта из ответа провайдера обязаны совпасть со счётом; иначе платёж не применяется, в журнал пишется `critical` и запись аудита `billing.amount_mismatch`. Из подписанного уведомления Т-Банка берётся только `RebillId` (в `GetState` его нет).
3. **Идемпотентность.** `webhook_events` с `UNIQUE(provider, event_id)` (у ЮKassa идентификатор события собирается как `событие:id платежа`, у Т-Банка `PaymentId:Status`). Если обработка упала, запись удаляется и ответ 503, чтобы повтор провайдера не приняли за дубль. Применение платежа (`BillingService::apply`) блокирует строки в порядке платёж → счёт → подписка, повторное применение ничего не меняет. Провайдер никогда не вызывается внутри транзакции БД.
4. **Деньги пришли за отменённый счёт.** Новый выбор тарифа отменяет прошлый неоплаченный счёт (один открытый счёт на пространство). Если платёж по нему всё-таки прошёл (человек оплатил старую вкладку), он записывается в журнал проводок и аудит (`billing.payment_orphaned`), но подписку не меняет, иначе периоды наложились бы; возврат решает владелец сервиса.
5. **Статус из провайдера, а не из возврата в браузер.** Страница возврата сама спрашивает провайдера, а раз в час планировщик опрашивает платежи, висящие дольше пяти минут (потерянное уведомление не оставляет оплату неприменённой).
6. **Арифметика только в целых копейках.** Апгрейд внутри периода: доплата = разница цен × (остаток / длина периода), округление до копейки, минимум 1 ₽ (меньше провайдеры не принимают); срок не меняется. Другой срок того же тарифа в бо́льшую сторону или смена на тариф с другим сроком: новый период с зачётом неиспользованного остатка. Всё, что дешевле, записывается на конец оплаченного периода и ничего не стоит сейчас. Месяц считается с зажимом по концу месяца (31 января + 1 мес = 28 февраля).
7. **Продление.** Первая попытка за `lead_days` (3) до конца, после неудачи повторы через 1 и 3 дня от первой попытки (то есть за 2 дня и в день окончания), письмо при каждой неудаче; после окончания срока 3 дня отсрочки, затем Free. Сбой связи с провайдером попыткой не считается и повторяется через час. Отменённая подписка уходит на Free в момент окончания периода без отсрочки; пробный период по окончании.
8. **Лимиты проверяет сервис, а не страница** (`Entitlements`): каналы, посты, команда, место в медиатеке, число пространств, возможности (`PlanFeature` для маршрутов и `assertFeature` для сервисов). Правила подсчёта: каналы считаются, пока не на паузе (глобальный потолок `CHANNELS_MAX` считает все); месяц постов считается в часовом поясе пространства и включает запланированные и опубликованные (черновики и отменённые не считаются; перенос внутри месяца бесплатен); в команду входят все роли и открытые приглашения; число пространств владельца определяется самым щедрым тарифом среди его пространств, остальные пространства стартуют на Free, пробный период только у первого (личного).
9. **При переходе на меньший тариф ничего не удаляется.** Лишние каналы (самые новые) ставятся на паузу с причиной, запланированные в них посты отменяются с причиной; участники, файлы и пространства сверх лимита остаются, запрещается только добавлять новое.
10. **Цены в БД.** `config/billing.php` — стартовый каталог; миграция и `billing:plans --sync` добавляют только недостающее и ничего не перезаписывают, поэтому цены меняются в админке (этап 20) без деплоя. Кэша тарифов нет (долгоживущий worker не должен видеть старые цены).
11. **Фейковый шлюз** хранит «состояние провайдера» в `payments.provider_status`, уведомлений не шлёт, недоступен в production. Каждый платёж «создаёт» собственную карту (идентификатор способа оплаты уникален для пространства).
12. **PDF-квитанция без библиотеки.** Квитанция — одностраничный PDF, который пишет `Support/Pdf/TextPdf` (встроенный шрифт DejaVu Sans из образа, `ToUnicode` для копирования текста). Это квитанция об оплате сервиса, а не фискальный чек: чек 54-ФЗ присылает онлайн-касса провайдера на почту плательщика. Данные продавца (ИП, ИНН) — `BILLING_SELLER_NAME`, `BILLING_SELLER_INN`.
13. **Идентификаторы способов оплаты** (`payment_method_id` ЮKassa, `RebillId` Т-Банка) хранятся открытым текстом: без наших ключей магазина ими нельзя списать деньги, а уникальный индекс нужен для защиты от переноса способа оплаты в чужое пространство. Номера карт не попадают к нам вообще.

## Что не проверено (нужны тестовые магазины владельца)
- Коды НДС ЮKassa (`vat_code`) и значения `Tax` Т-Банка для ставок 20/22 %: для ИП на УСН без НДС (по умолчанию `none` = 1 / `none`) проверено по документации, остальные нужно сверить перед включением.
- Чек возврата Т-Банка: полный возврат формирует чек сам, для частичного может понадобиться `Receipt` в `Cancel` (сейчас не передаётся; возврат из интерфейса пока недоступен, только сервис).
- Поведение ЮKassa при автоплатеже с `payment_method_id` без 3-D Secure (ожидается `succeeded` сразу или `pending` с уведомлением; оба случая обработаны).
- `GetState` Т-Банка не возвращает `RebillId`: карта сохраняется из подписанного уведомления. Если у владельца уведомления не доходят, автопродление не включится (оплата при этом применится).
- Если ответ на списание ЮKassa потерян три раза подряд после фактического списания, платёж без `provider_payment_id` не будет найден (защита: один и тот же `Idempotence-Key` на повторах внутри попытки).

## Последствия
- Новый домен `Domain/Billing`, интеграции `Integrations/Payments`, 11 таблиц; env `YOOKASSA_*`, `TBANK_*`, `BILLING_*`.
- `CHANNELS_MAX` стал глобальным потолком (по умолчанию 1000), `MEDIA_QUOTA_MB` необязательным глобальным ограничением сверху (по умолчанию 0, то есть нет); размер медиатеки и число каналов берутся из тарифа.
- Для этапов 13–18: возможности проверяются `PlanFeature` и `Entitlements::assertFeature`; метрики AI-кредитов кладутся в `usage_counters`.
