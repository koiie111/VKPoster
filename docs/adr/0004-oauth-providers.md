# 0004. Вход через соцсети без внешних OAuth-библиотек

- Статус: принято
- Дата: 2026-10-04

## Контекст
Этап 03 добавляет вход через VK ID, Яндекс ID, Google и Telegram. Белый список зависимостей (ENGINEERING_RULES §2) не содержит OAuth-клиента и JWT-библиотеки. Google возвращает подписанный `id_token` (RS256), и план требует проверять подпись по JWKS.

## Решение
Не добавлять зависимости. Провайдеры реализованы на `HttpClientInterface` (30–80 строк на провайдера: URL авторизации, обмен кода, профиль). Проверка `id_token` — класс `JwtVerifier`: принимается только RS256, ключ берётся из JWKS по `kid` и собирается в PEM вручную (ASN.1 DER на ~20 строк), подпись проверяет `openssl_verify`, затем `iss`, `aud`, `exp`, `iat`, `nonce`. Telegram проверяется HMAC-SHA256 по документации Telegram, без внешнего кода.

## Рассмотренные варианты
- **`league/oauth2-client` и провайдеры.** Покрывают поток кода, но не PKCE для VK ID/Яндекса из коробки и тянут несколько пакетов; VK ID (id.vk.com) и Telegram всё равно пришлось бы писать самим.
- **`firebase/php-jwt` или `web-token/jwt-framework`.** Надёжны, но нужны ради одной проверки RS256; наша реализация закрыта тестами на `alg=none`, подмену алгоритма, чужой ключ, `aud`, `iss`, `exp`, `nonce`.

## Последствия
- Новых зависимостей нет, `composer audit` не меняется.
- Если понадобятся другие алгоритмы (ES256) или кэш JWKS, расширяем `JwtVerifier` или заменяем библиотекой отдельным ADR. JWKS сейчас запрашивается при каждом входе через Google (редкая операция).
- Права на публикации не запрашиваются при входе: каналы подключаются отдельно (этапы 06–09).
- Точные параметры VK ID (`device_id`, `client_secret`) и Яндекса сверяются при живой проверке владельцем.
