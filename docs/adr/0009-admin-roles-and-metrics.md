# 0009. Роли персонала в коде, бизнес-метрики из счетов и журнала проводок

- Статус: принято
- Дата: 2026-10-05

## Контекст
Этап 20 (полная админка владельца) предлагает таблицы `staff_roles`, `analytics_events`, `metrics_daily` и дашборд с MRR, оттоком, LTV, когортами. Нужно решить, где живут права ролей, откуда считать деньги и как не получить цифры, которые расходятся с реальностью.

## Решение
1. **Права ролей лежат в коде** (`config/admin_permissions.php`: право → роли), а в БД только назначение (`staff_members`: пользователь и роль). Отдельной таблицы `staff_roles` нет: правка прав через БД обходит ревью, а набор ролей из пяти штук не требует таблицы. Владелец (`users.is_superadmin`) имеет все права. Каждый маршрут `/admin` называет ровно одно право (`RequireStaffPermission`), тест обходит всю таблицу маршрутов и сверяет матрицу «роль × маршрут».
2. **Деньги и MRR считаются из счетов и журнала проводок, а не из событий.** MRR на момент `t` = сумма месячных эквивалентов `list_price` оплаченных счетов, период которых накрывает `t` (при пересечении побеждает счёт с более поздним началом; полностью возвращённые платежи не считаются; подарок без оплаты не считается). Выручка и возвраты берутся из `ledger_entries`. Благодаря этому любой прошлый день можно пересчитать и получить то же самое, а пропущенное событие не портит цифры. `analytics_events` остаётся сырым потоком (визиты, регистрация, оплаты, пробный период; из него берётся только верхний шаг воронки) и хранилищем для будущих функций (AI, рефералка).
3. **Источник трафика хранится в сессии, а не в постоянной cookie.** UTM и host реферера первой страницы сессии пишутся в `user_attribution` при регистрации. Сессионная cookie необходимая; никаких долгоживущих трекеров нет (152-ФЗ, баннер cookies обещает аналитику только после согласия).
4. **Chart.js 4.4.7** положен в `public/assets/vendor` с SHA-256 (разрешён правилами §2); CDN нет. Графики рисует `js/admin-charts.js` по JSON из атрибута, у каждого есть таблица с теми же числами.
5. **Опасные действия** требуют свежий код аутентификатора в самой форме (`StepUp`), а не только разблокировку админки. Использованный код повторно не принимается (общий механизм TOTP).
6. **Цвета сайта** (`Дизайн и цвета`): переопределение хранится в `app_settings`, отдаётся отдельным CSS `/theme.css?v=хэш` после основного; inline-стили запрещены CSP. «Сбросить» удаляет настройку.

## Рассмотренные варианты
- Права ролей в таблице: гибче, но правка вне git и без ревью; отклонено.
- MRR из событий `subscription_*` с дельтами: прошлое невосстановимо при пропуске события; отклонено.
- Постоянная first-touch cookie с согласием: возможна позже при включении аналитики; сейчас достаточно сессии.
- XLSX для бухгалтерии: нужен `phpspreadsheet` (разрешён по §2, но этап 13 его ещё не подключил). CSV с BOM и `;` открывается в Excel без настройки; XLSX перенесён.

## Последствия
- Дашборд читает `metrics_daily`; планировщик пересчитывает последние 3 дня каждый час (идемпотентно), `make seed-demo` строит полгода демо-данных.
- Данные до начала этапа не имеют истории подписок кроме счетов: исторический MRR честно получается только из оплаченных счетов (то, что и есть правда о деньгах).
- Промокоды и рефералка (раздел этапа 20 «Финансы») не сделаны здесь: они меняют оформление заказа и появляются в этапе 16, который обязан добавить свои разделы в админку (ENGINEERING_RULES §7).
- Себестоимость AI и маржа показываются из событий `ai_used`; пока AI нет, нули.
