# 0006. Публикация в VK: токен пользователя через VK ID OAuth 2.1 и свой клиент API

- Статус: принято, требует живой проверки владельцем (см. «Что не проверено»)
- Дата: 2026-10-04

## Контекст
Этап 08 публикует на стены сообществ VK. Нужно выбрать, каким токеном вызывать методы `wall.*`, `photos.*`, `video.*`, `docs.*`, `polls.*`, `groups.get`, и чем их вызывать. Страницы `dev.vk.com` из среды разработки недоступны (сайт не открывается автоматизированным клиентом), поэтому выводы опираются на `id.vk.ru` (документация VK ID), схему API (`VKCOM/vk-api-schema`) и публичные обсуждения. Всё, что не удалось подтвердить по первоисточнику, помечено ниже.

## Что известно
- Токен сообщества (ключ доступа) вызывает `wall.post` с текстом, но `photos.getWallUploadServer` отвечает ошибкой 27 «Group authorization failed», даже когда право `photos` выдано ([vk-api-schema#242](https://github.com/VKCOM/vk-api-schema/issues/242)). Загрузка фото на стену сообщества требует **токена пользователя**.
- VK ID (OAuth 2.1, PKCE) выдаёт пару: `access_token` (60 минут), `refresh_token` (180 дней, **одноразовый**: после обновления старый перестаёт работать, повторное использование старого отзывает всю сессию) и `id_token`. Обновление: `POST https://id.vk.com/oauth2/auth`, `grant_type=refresh_token`, `refresh_token`, `client_id`, `device_id` (приходит в callback и обязателен), `state`.
- Права на API (`wall`, `photos`, `video`, `docs`, `groups`) запрашиваются параметром `scope` на `https://id.vk.com/authorize`; токен передаётся как `Authorization: Bearer …` или `access_token=`.

## Решение
1. **Один способ: токен пользователя из VK ID OAuth 2.1.** Человек входит через VK с правами `wall photos video docs groups` (`VK_SCOPE`), мы получаем список его сообществ (`groups.get` с `filter=admin,editor`), он выбирает, какие подключить. Режим `ChannelMode::Account`: публикует аккаунт человека от имени сообщества (`from_group=1`). Ключ сообщества как второй способ не делаем: он не умеет загружать фото, а половина постов с картинками.
2. **Одна запись `platform_credentials` на вход, много каналов.** Все сообщества, выбранные за один вход, ссылаются на один `credential_id`. Обновление токена идёт по этой записи под замком Redis (`oauth:refresh:{id}`): кто взял замок, обновляет и сразу сохраняет новую пару; остальные ждут результата до 12 секунд. Одноразовость refresh-токена делает замок обязательным. Столбцы `device_id` и `account_id` добавлены миграцией 000013.
3. **Обновление за 5 минут до конца жизни**, чтобы долгая загрузка видео не начиналась с токеном на пороге истечения. Если VK отверг refresh-токен, это `auth`: канал помечается сломанным, владелец получает письмо и переподключает. Если VK недоступен, это `temporary`: пара остаётся нетронутой.
4. **Свой клиент API**, без `vkcom/vk-php-sdk`: пакет вне белого списка зависимостей, а нужно ~15 методов. Версия API 5.199 (`config/platforms.php`). Токен только в заголовке, исключения транспорта не цепляются (в URL и сообщения токен не попадает). Лимит ~3 запросов в секунду на токен держит `VkRateGate` на Redis.
5. **Повтор безопасен в пределах часа через `guid`:** в `wall.post` передаётся `md5(idempotency_key)`. Но политика конвейера не меняется: обрыв после отправки остаётся `unknown_outcome`, **и перед тем как беспокоить владельца, адаптер сверяет последние 20 постов стены** (`OutcomeVerifier`: совпадение по тексту без учёта пробелов, автору-сообществу и времени не раньше начала попытки; для постов без текста по числу вложений). Найденный пост считается успехом.
6. **Суточный лимит** (~50 постов на сообщество, `VK_POSTS_PER_DAY`) проверяется при планировании и переносе (`Capabilities::$maxPostsPerDay`): день в часовом поясе пространства, отменённые не считаются.

## Рассмотренные варианты
- **Токен сообщества.** Проще (не истекает), но нет загрузки фото. Отклонено.
- **Implicit flow / «бессрочный» токен (`offline`) старого OAuth `oauth.vk.com`.** Не получает refresh и считается устаревшим; VK ID — основной путь. Отклонено.
- **`vkcom/vk-php-sdk`.** Не в белом списке, тянет лишнее, ошибки не классифицируются под наш конвейер.

## Что не проверено (нужна живая проверка владельцем)
- Выдаёт ли VK ID приложению права `wall photos video docs groups` сразу или нужна заявка/модерация (в плане этапа это отмечено как возможное). Если заявка нужна, это решение владельца: подать её в кабинете `id.vk.com`.
- Точное поведение `wall.edit` без `attachments` (мы всегда передаём текущие вложения заново, это безопасно в обоих случаях) и размер полей опроса (лимиты в `validate()` намеренно мягкие: лучше ошибка 100 от VK с понятным текстом, чем ложный отказ).
- Принимает ли VK ID `Authorization: Bearer` для `api.vk.com` (по документации да; если нет, достаточно перенести токен в параметр `access_token` в `VkApi::call`).

## Последствия
- Права и срок жизни токена видны владельцу только косвенно (канал «нужно переподключить» через ≤180 дней без публикаций; публикации сами продлевают пару).
- Новых зависимостей нет.
- Сроки: если refresh-токен не использовался 180 дней, канал придётся подключить заново; ежедневная проверка здоровья каналов (раз в 6 часов) вызывает `groups.get` и поэтому продлевает пару.
